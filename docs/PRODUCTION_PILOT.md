# Первый production-пилот Hookah_Tootah

Профиль обслуживает `@hookah_tootah_bot` и `https://hookahtootah.club/miniapp/`
на отдельном VPS. Он использует опубликованный backend со встроенным same-origin
Mini App, PostgreSQL 17 и системный Caddy. Для PostgreSQL предусмотрены отдельная
БД `hookah_prod`, роль приложения `hookah_app` без административных прав и том
`hookah_production_pgdata`. PostgreSQL доступен только в закрытой Docker-сети.
Backend работает от UID 10001, с read-only rootfs, публикует только
`127.0.0.1:18080` и имеет отдельную сеть для исходящих соединений.

## До выделения сервера

- Нужен Linux x86-64. GHCR публикует backend для `linux/amd64`. Ориентир для
  ограниченного пилота без PDF — 2–3 vCPU, 4 ГиБ RAM, от 40 ГиБ SSD. Репетиция
  прошла с 3 vCPU и 4 ГиБ, при этом на прогретом пустом стенде backend занимал
  около 342 МиБ, PostgreSQL около 138 МиБ. Нижняя граница CPU и одновременные
  пользовательские нагрузки требуют замеров. По диску учитывайте два образа,
  рост БД/WAL, ограничение Docker-логов и место под зашифрованную копию.
- На выделенном хосте нужны Docker Engine с `image inspect --platform`, Compose
  с `config --hash`, Python 3.9+, Bash, GitHub CLI с доступом на чтение к
  Actions artifacts, `age`, `shasum` и Caddy 2. Разместите checkout с проверенным
  профилем на постоянном пути. Закрепите файлы init SQL, traffic-gate.sh и Caddyfile из этой версии; изменять их может только оператор.
  Доступ к Docker и приватным файлам имеет оператор. Настройте лимит и ротацию
  Docker-логов, синхронизацию времени, обновления ОС и мониторинг заполнения диска.
  Открываются TCP 80/443 и административный SSH с разрешённых адресов.
- Заранее согласуйте, кто обслуживает уже выданные ссылки `/v/…` на apex,
  и какие QR/ссылки ведут в staging. Идентификаторы заведений из независимых
  баз могут совпадать. Переключение общего apex без инвентаризации может
  отправить старую ссылку в другое заведение. В production используется формат
  `/v/<slug>`. Wildcard и staging-поддомены требуют собственного плана.
- Определите Platform Owner, подтвердите ручной биллинг, ограничения загрузок,
  бюджет, off-site хранение и полномочия на восстановление. Профиль HT70,
  staging-бот и серверные файлы staging для этого не нужны.

## Подготовка кандидата

Работайте на будущем выделенном production-хосте из корня проверенного checkout.
Оператор назначает `P` приватным каталогом вне Git с правами 0700, а `RUN`,
`SHA`, `ATTEMPT` берёт из завершённого успешного push CI на main. Команды
ниже предназначены для отдельно разрешённого запуска.

```bash
set -euo pipefail
umask 077
export DOCKER_HOST=unix:///var/run/docker.sock
unset DOCKER_CONTEXT COMPOSE_PROJECT_NAME COMPOSE_FILE
install -d -m 700 "$P"
test ! -e "$P/runtime.env"
install -m 600 deploy/production/runtime.env.example "$P/runtime.env"
gh run download "$RUN" -R koteev-m/hookah_bot \
  -n "ghcr-candidate-${SHA}-${ATTEMPT}" -D "$P/ci-$SHA"
```

Копируйте шаблон только при первом вводе. Заполните `runtime.env` в приватном
редакторе. Каждая из шести величин в hex — независимые 32 случайных байта из
production-хранилища. Выберите и запишите digest официального одобренного
PostgreSQL 17. Бот изначально выключен, поля token и owner пусты. Значения
паролей Postgres применяются entrypoint только на пустом томе. Ротация для
существующей БД требует согласованных SQL, runtime и проверки соединения.
Все секреты, включая будущий Telegram token, должны иметь отдельное хранение
вне VPS. Доступ к Compose-плану и Docker inspect равнозначен доступу к секретам.

```bash
profile=(python3 -B scripts/production_profile.py)
plan="$P/release-$SHA.json"
ci="$P/ci-$SHA/candidate.json"
"${profile[@]}" check "$P/runtime.env" "$ci"
"${profile[@]}" admit "$P/runtime.env" "$ci" "$plan"
dc=(docker compose --env-file /dev/null -p hookah_production -f "$plan")
```

`check` валидирует шаблон без внешнего доступа. `admit` проверяет repository,
событие push, ветку main, workflow CI, полный SHA и успешное завершение.
Он сверяет candidate с артефактом publishing job **этой попытки**, immutable
digest, OCI source/revision, linux/amd64, версию PostgreSQL и все SQL в JAR
до V143 включительно и поддержку привязки допуска к экземпляру JVM в JAR.
Образы до появления этой поддержки требуют нового релиза. При включённом боте он сверяет токен вызовом `getMe`.
Приватный Compose-план создаётся атомарно по новому пути. В файл попадают
секреты, поэтому его содержимое следует исключить из терминальных логов,
артефактов CI и Git.

## Первая установка и проверка

Перед первой установкой при пустом проекте следующие команды должны завершиться успешно. При существующем томе или контейнерах выясните их происхождение
до запуска. Проверьте и отсутствие занятого порта 18080.

```bash
containers=$(docker ps -a --filter label=com.docker.compose.project=hookah_production --format '{{.Names}}')
volumes=$(docker volume ls --format '{{.Name}}' | awk '$0=="hookah_production_pgdata"')
networks=$(docker network ls --format '{{.Name}}' | awk '/^hookah_production_/')
listeners=$(ss -Hlt 'sport = :18080')
test -z "$containers$volumes$networks$listeners"
```

Установите production Caddyfile на выделенном хосте и проверьте его через
`caddy validate`. Системный Caddy читает каталог допуска. Его владелец —
администратор, права 0755. Первое открытие потребует доверенного локальному
клиенту HTTPS-сертификата для apex. До согласованного переключения DNS
репетицию проводят с отдельным тестовым CA и локальным разрешением имени.

```bash
install -d -m 0755 /var/lib/hookah-production/ingress
test ! -e /var/lib/hookah-production/ingress/open
traffic=(python3 -B scripts/production_traffic.py)
"${dc[@]}" up -d --pull never
"${profile[@]}" running "$plan"
python3 deploy/production/smoke.py "$plan"
"${dc[@]}" exec -T postgres psql -XqAt -v ON_ERROR_STOP=1 -U hookah_app -d hookah_prod \
  < deploy/production/history.sql | "${profile[@]}" history
```

`running` сверяет образы, Compose hashes обоих сервисов, том и сетевые привязки.
Smoke ожидает `ok` от `/health` и `/db/health`, `prod` и точный SHA от
`/version`, HTML/JS/CSS под `/miniapp/` и HTTP 401 от гостевого API без сессии.
Smoke читает index.html и полные entry JS/CSS из локального образа по digest
с `--pull never` и отключённой сетью. Он сверяет размер и SHA-256 каждого
ответа с этими байтами, а также MIME и same-origin URL. Проверка history требует 143 успешные записи в порядке установки, с точными
именами и Flyway checksums репозиторных миграций V1–V143.

После проверки свежей V143 оператор сверяет кластер, volume и публичный ключ
age с хранителем. Единожды зарегистрируйте БД и получателя в приватном
каталоге всех допущенных планов. Сохраните независимую защищённую копию
`postgres-binding.json`. Замена PostgreSQL-контейнера тоже изменяет привязку.
При расхождении требуется отдельная идентификация БД и решение владельца.
Повторная регистрация во время аварии скрыла бы причину отказа.

```bash
"${profile[@]}" bind-db "$plan" "$RECIPIENT"
# Выполните браузерную проверку по loopback, описанную ниже.
"${traffic[@]}" open "$plan"
```

Диагностика обновления через `inspect OLD NEW` возвращает ненулевой код для UNKNOWN и отсутствующего backend. Сохраните вывод и выясните причину до следующей операции.

## Backup и проверочное восстановление

Назначьте `POINT` новым путём каталога и `RECIPIENT` публичным age-получателем
независимого хранителя. Секретный ключ восстановления держите у хранителя.
Backup работает при healthy, stopped или unhealthy backend. Он проверяет образ,
здоровье и Compose hash PostgreSQL, контейнер, сеть и том, идентификатор кластера,
OID/владельца БД, Flyway V1–V143 и зарегистрированного получателя. При отказе
сохраните привязку и выясните причину. Backup создаёт custom-format pg_dump в потоке через age и перечень SHA-256.
Каталог без готового `SHA256SUMS` неполон. Скопируйте завершённую точку во
внешнее хранилище с независимыми правами, сохраните идентификатор версии и
проверьте считанные обратно байты. Digest PostgreSQL должен происходить из
доверенной конфигурации.

```bash
deploy/production/backup.sh "$plan" "$POINT" "$RECIPIENT"
# На изолированном restore-хосте с предзагруженным образом и тем же инструментарием
deploy/production/restore-test.sh "$POINT" "$AGE_IDENTITY_FILE" "$APPROVED_PG_DIGEST"
```

Restore проверяет SHA-256, расшифровку, всю загрузку архива в одной транзакции,
историю Flyway и `pg_amcheck`. Он поднимает отдельный PostgreSQL с новым
именованным томом, без сети, портов и Docker-логов. Для каждой попытки
оператор использует того же системного пользователя, Docker daemon и постоянный
приватный `${XDG_STATE_HOME:-~/.local/state}/hookah-production-restore`.
Журнал фиксирует daemon, digest и UUID до выделения ресурсов. После обрыва
повторный запуск проверяет имена, метки, подключения и владельца тома, убирает
остатки прошлой попытки и начинает новую. Сообщение об успехе появляется после
проверки удаления контейнера и тома. При неизвестном ресурсе или ошибке удаления
сохраните журнал и ограничьте доступ администраторам до разбора. Защитите диск
restore-хоста шифрованием, поскольку данные в тестовом томе расшифрованы.
По желанию четвёртым аргументом передаётся доверенный SQL-файл с проверками,
которые завершаются ошибкой при потере контрольных данных. Реальную копию
проверяет независимый оператор в изолированной среде. Возврат данных в рабочую
БД требует отдельного решения о точке восстановления и допустимой потере.

Этот дамп покрывает одну БД приложения. Роль пересоздаётся штатным init SQL,
секреты, образ, DNS/TLS, конфигурация бота и внешние медиа требуют отдельного
хранения. До реальных данных владелец должен обеспечить и подтвердить
production-процедуру по Policy B. В действующей политике предусмотрены снимок
каждые 6 ч, квалификация за 2 ч, контроль каждые 5 мин, 7 дней хранения и
минимум две пригодные точки. Локальная репетиция подтверждает операции
backup/restore только на синтетических данных. [Политика восстановления](DEPLOYMENT_RUNBOOK.md#policy-b-disaster-recovery--ht-ops-04--ap-01).

## Обновление действующей версии

Один оператор ведёт обновление из постоянного проверенного checkout. `OLD` и
`NEW` — приватные планы в каталоге с исходным `postgres-binding.json`.
Сохраните SHA и immutable digest обоих образов. `admit --previous` сверяет
происхождение нового коммита, зелёный main CI и разрешает изменить только
backend digest и revision. План сохраняет обе пары SHA/digest и версию схемы.
При обновлении с V142 Flyway применяет один файл `V143__billing_courtesy_operation.sql`
с checksum `1900727557`. Он добавляет ключ и результат операции начисления льготы.
После запуска проверьте текущую версию 143, 143 успешные записи истории, 0 pending
и 0 failed. Контракт CI сверяет имя и SHA-256 каждого файла после исторической V126.
На staging с V142 изменение вступит в силу только при отдельном запуске нового backend
на его БД. Исторический cutover для V126 продолжает отклонять более новые схемы.
Изменение схемы выше V143, runtime, сети, образа
PostgreSQL или включение бота требует отдельного решения.

```bash
traffic=(python3 -B scripts/production_traffic.py)
"${profile[@]}" running "$OLD"
"${profile[@]}" admit "$P/runtime.env" "$NEW_CANDIDATE" "$NEW" --previous "$OLD"
"${traffic[@]}" close "$OLD"
deploy/production/backup.sh "$OLD" "$POINT" "$RECIPIENT"
```

`close` убирает постоянный маркер, останавливает процесс OLD вместе с polling
и подтверждает по HTTPS через loopback ответ 503 с заголовком
`X-Hookah-Maintenance: closed`. Затем снова запускает OLD в закрытом режиме
и проверяет его готовность. Во время backup и квалификации оператор может
проверять health, DB health, version и Mini App на `127.0.0.1:18080`.
При замене процесса в `stage` эти endpoints кратко недоступны; PostgreSQL
проверяется напрямую. Клиентский ingress и polling остаются закрыты при
перезапуске контейнера или ОС.

Получите результат restore-test для этой точки из независимого хранилища.
Запишите идентификатор копии. Только затем продолжайте.

```bash
"${traffic[@]}" stage "$OLD" "$NEW"
"${traffic[@]}" inspect "$OLD" "$NEW"
python3 deploy/production/smoke.py "$NEW"
```

Пока ingress закрыт, откройте `/miniapp/` в Chromium через защищённый туннель
на loopback оператора. Проверьте отрисовку содержимого внутри `#app`, загрузку
стилей и отсутствие ошибок модуля. HTTP smoke отдельно проверяет статус,
same-origin URL, MIME и содержимое entry JS/CSS. Разрешите трафик только после
успеха этих проверок и решения оператора.

```bash
"${traffic[@]}" open "$NEW"
"${traffic[@]}" inspect "$OLD" "$NEW"
```

`open` проверяет закрытый HTTPS, образы, привязку PostgreSQL и V1–V143,
затем выполняет loopback smoke на окончательной JVM. `/version` возвращает
SHA, уникальный для запуска `instance` и состояние polling. Пока вход закрыт,
проверенная JVM обслуживает административные запросы. Замены процесса
при открытии нет.

Операторская команда атомарно сохраняет в `activate` пару SHA и instance.
Для включённого бота тот же процесс проверяет отсутствие webhook и приобретает
единственную аренду polling. Первый успешный ответ getUpdates от этого worker обязателен для running.
Worker делает до трёх попыток с backoff в серии. Без подтверждения дольше long-poll timeout плюс 15 секунд
готовность теряется. В репетиции с TELEGRAM_BOT_ENABLED=false ожидается disabled и пустые реквизиты. Новый процесс не может использовать прежнюю пару.
После подтверждения `running` (или `disabled` для выключенного бота), повторных
проверок Flyway, контейнеров, assets и instance команда сохраняет эту же пару в
`open`. Caddy добавляет служебный заголовок к публичному запросу. Backend
проверяет оба решения и состояние poller перед обработкой такого запроса.
Перед каждым публичным запросом JVM проверяет соединение с PostgreSQL. Одновременные
запросы разделяют выполняющуюся проверку. При открытом входе выполняется также один
фоновый контроль в секунду. Отказ БД или утрата готовности polling отзывает допуск
этой JVM. Публичный HTTP отвечает 503, в том числе после возвращения БД. Для диагностики
используйте loopback /health, /db/health и /version. После устранения причины выполните
явный close для текущего плана, проверьте новую JVM, затем open. Сохранённый маркер
после SIGKILL или reboot сам по себе не открывает вход.

При несовпадении instance публичные операции закрыты. Не публикуйте loopback
порт backend. После допуска проверьте публичные HTTPS health/version/Mini App
и, в разрешённом окне, вход через настоящий Telegram.

**После обрыва сессии** выполните `"${traffic[@]}" inspect "$OLD" "$NEW"`.
Инспекция проверяет привязку PostgreSQL и показывает фактическую версию,
состояние backend и оба решения оператора. Сверьте их с loopback `/version`.

| Наблюдение | Действие оператора |
| --- | --- |
| CLOSED, NEW stopped | Запустите `"${traffic[@]}" resume "$OLD" "$NEW"`. Команда повторно проверит DB binding и точный контейнер NEW, запустит его по ID, сверит Flyway, health, version и assets. PostgreSQL продолжит работать. Выполните браузерный smoke, затем явно вызовите `open "$NEW"`. |
| CLOSED, NEW running | Повторите loopback smoke по плану NEW и браузерную проверку. После SIGKILL во время resume контейнер уже может работать. Если прервался open, polling мог начать работу для указанного instance при всё ещё закрытом HTTP. Повторный явный open сверит тот же процесс и его готовность. |
| CLOSED, OLD | Проверьте drain, локальный health, состояние polling и квалификацию backup перед оставшимся шагом обновления. |
| Сохранён open | Сверьте SHA и instance с живым ответом через HTTPS. Если JVM перезапустилась, обёртка ждёт снятия прежнего решения. Выполните close для идентифицированного плана и повторите квалификацию. |
| Неизвестный контейнер, изменённые digest, том, сеть или cluster ID | Сохраняйте ingress закрытым. Зафиксируйте исходную привязку, оба плана и диагностику. Замена PostgreSQL, повторный bind, rollback или restore требуют отдельного решения. |

При ошибке запуска polling сохраните закрытый HTTP, устраните причину ошибки
бота, затем выполните close для подтверждённого плана и проверьте новую JVM.
Маркер вручную не создаётся. Вне Git сохраняется исходный защищённый каталог
оператора, включая привязку БД и допущенные планы.

## Домен и Telegram

1. После решения по старым ссылкам настройте на новом сервере системный Caddy
   с [production Caddyfile](../deploy/production/Caddyfile). Укажите только
   apex `hookahtootah.club`. Проверьте конфигурацию `caddy validate`.
   Согласуйте TTL, окно и возврат DNS, отдельно проверьте A и AAAA. Менять
   staging, wildcard-записи и профиль staging-бота эта процедура не требует.
2. В разрешённое окно направьте apex на production VPS и подтвердите выпуск
   доверенного сертификата, `/health`, точный `/version`, assets и
   `/miniapp/` по HTTPS. На edge закрыты billing webhooks и внутренние
   диагностики. Запрос с посторонним браузерным Origin получает 403.
3. Для включения бота подготовьте отдельный токен `@hookah_tootah_bot` и
   положительный Telegram ID Platform Owner. Проверьте отсутствие другого
   poller и пустой webhook через Telegram для **этого** бота. В приватном
   runtime задайте token, owner, `TELEGRAM_BOT_ENABLED=true`. Выполните отдельный
   допуск конфигурации на прежнем digest в новый план, проверьте разницу
   разрешённых полей приватно, закройте предыдущий план через `close`, примените
   backend в закрытом режиме и проверьте loopback. После явного `open`
   запустятся long polling и настройка меню бота. Проверяются `/start`, кнопка меню,
   подписанный вход через Mini App, права владельца и доступ гостя.
4. В BotFather владелец задаёт Main Mini App URL
   `https://hookahtootah.club/miniapp/` для `@hookah_tootah_bot`. До
   подтверждения на устройстве оставьте `TELEGRAM_MAIN_MINI_APP_CONFIGURED=false`.
   После проверки `startapp` включите флаг отдельным изменением конфигурации.
   Проверьте личную ссылку опубликованного production-заведения с несколькими

## Границы пилота

- `BILLING_PROVIDER=fake` поддерживает счета, ручную отметку оплаты Platform
  Owner и льготные дни с основанием. Он не списывает деньги, не даёт рабочую
  платёжную ссылку и не подтверждает банковский расчёт. Автоматический биллинг в пилоте **OFF**. Итоговый Compose задаёт
  `BILLING_SUBSCRIPTION_INTERVAL_SECONDS=0`. Задача не готовит счета и
  напоминания, не переводит заведения в `PAST_DUE` и `SUSPENDED_BY_PLATFORM`.
  Владелец ведёт календарь окончания trial и льгот и явно принимает решение
  о продлении на конкретный срок или о статусе заведения.
  За период с ценой 0 ₽ платёжный счёт не создаётся. Более ранние платные
  обязательства сохраняются. В Venue и Platform откройте «Неоплаченные счета».
  У каждого счёта есть свой ID, сумма, срок и статус. «Открыт» допускает будущий
  срок оплаты, «Просрочен» соответствует `PAST_DUE`. Разверните нужную запись
  по номеру. Ручная отметка оплаты применяется только к выбранному счёту.
  Список показывает до 50 неоплаченных счетов за раз в порядке ID, начиная
  со старых. При наличии продолжения нажмите «Следующие неоплаченные счета».
  Ошибка загрузки требует повторной проверки. История последних 50 счетов
  и совместимое поле API `payableInvoice` сохраняют прежнее значение.
  Дату следующего платежа показывает только явное поле ответа сервера. Бесплатный период сам по себе не меняет статус
  подписки. Для гостевых операций опубликованного заведения resolver допускает
  TRIAL, ACTIVE и PAST_DUE. UNKNOWN, CANCELED и приостановка закрывают эти
  операции. Просмотр публичной ссылки при отсутствующей строке подписки имеет
  отдельный read-only контракт. На части гостевых маршрутов сохраняется
  существующая ленивая инициализация TRIAL. Перед приглашением гостей задайте
  явный статус и дату пересмотра. Серверные проверки прав действуют.
  Реальный эквайринг,
  Stars и автосписания выходят за пределы пилота. [Биллинг и подписки](PLATFORM_COCKPIT.md#billing--subscriptions--invoices).
- Оба R2-флага выключены. Новые прямые загрузки фото сотрудников,
  информационных JPEG/PNG, файлов PDF и графических планов залов недоступны.
  Worker для этого набора функций не нужен. Структурированное меню и списки
  столов остаются отдельными функциями. Если пилоту нужны загрузки, сначала
  требуются отдельный production bucket/ключи, проверка доступа и восстановления
  объектов. Для новых PDF дополнительно нужен изолированный same-image worker с
  проверкой фактических OS-ограничений. [Контракт медиа](MEDIA_STORAGE_UPLOAD.md).

### Ручные льготы и оплата в пилоте

Для POST /api/platform/venues/{venueId}/billing/courtesy-days обязательны роль Platform Owner,
поля days и reason и заголовок Idempotency-Key с UUID. До отправки Mini App сохраняет ключ
операции в текущей сессии пользователя. Повтор возвращает первоначальный обзор, включая срок
льготы. Новый запрос после подтверждения получает новый UUID. При 428 обновите Mini App.
При 409 сверьте действие и его параметры. Уникальный ключ, корректировка, изменение статуса
и аудит фиксируются в одной транзакции. Клиентам предыдущих версий требуется обновление.

Фактическая оплата до даты basePaidThrough и льгота до courtesyUntil отображаются отдельно.
Исторический неоплаченный счёт доступен независимо от первых 50 строк истории и цены
нового периода. Настройки сохранённого бесплатного тарифа допускают изменение даты.
Явно заданные цены в форме изменения настроек по прежнему контракту должны быть положительными.
Платёж по старому периоду сохраняется в учёте. Он не снимает административную блокировку.

### Восстановление при административной блокировке подписки

В Platform откройте карточку заведения, обновите биллинг и проверьте основание доступа.
Для статуса `suspended_by_platform` введите обоснование и выберите «Снять блокировку подписки».
В отдельном диалоге подтвердите открытие гостевого доступа для опубликованного заведения.
Публикация, счета, платежи и история льгот сохраняют прежние значения.

Platform Owner вызывает `POST /api/platform/venues/{venueId}/billing/resume-subscription`
с полями `reason` и `expectedUpdatedAt`. Второе поле передаётся без преобразования из
`lifecycleUpdatedAt` последнего ответа `GET /api/platform/venues/{venueId}/billing`.
Сервер блокирует строку подписки в PostgreSQL и сверяет версию, подтверждённую владельцем.
При одновременной записи возврата он дожидается её исхода и повторно читает платёжные данные.
Успешный ответ содержит обновлённый billing overview. Запись аудита
`BILLING_SUBSCRIPTION_RESUMED` сохраняет исполнителя, причину, основание и переход статуса.

| Записи на момент подтверждения | Результат |
| --- | --- |
| Сегодня входит в период оплаченного счёта. Есть соответствующий успешный платёж той же суммы, валюты и провайдера, без зарегистрированного возврата | `ACTIVE` |
| Сегодня входит в предоставленные льготные дни, начиная со дня после `previous_paid_through` и по `new_paid_through` включительно. Начисление подтверждено его аудитом | `ACTIVE` |
| Время окончания действующего trial ещё не наступило | `TRIAL` |
| Только цена 0 ₽, старый платёж, будущая или истёкшая льгота | `409`, административная блокировка сохраняется |

В пилоте нет отдельного оформляемого права бесплатного доступа. Для его введения владельцу
потребуется определить срок, основание и способ отзыва. До этого цена 0 ₽ сама по себе даёт
`409`. Дату окончания trial или льготы оператор контролирует вручную, пока scheduler выключен.

При `409` обновите карточку. Повтор после успеха и запрос для прежней блокировки
не создают второго перехода или аудита. При сетевом сбое сначала перечитайте статус.
При отказе обязательной записи аудита сервер возвращает `503` и откатывает транзакцию.
Подтверждение поступления денег и вызовы webhook не снимают административную блокировку.
