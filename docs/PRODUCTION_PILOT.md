# Первый production-пилот Hookah_Tootah

Профиль обслуживает `@hookah_tootah_bot` и `https://hookahtootah.club/miniapp/`
на отдельном VPS. Он использует опубликованный backend со встроенным same-origin
Mini App, PostgreSQL 17 и системный Caddy. Для PostgreSQL предусмотрены отдельная
БД `hookah_prod`, роль приложения `hookah_app` без административных прав и том
`hookah_production_pgdata`. PostgreSQL доступен только в закрытой Docker-сети.
Backend работает от UID 10001, с read-only rootfs, публикует только
`127.0.0.1:18080` и имеет отдельную сеть для исходящих соединений.

## До выделения сервера

- Нужен Linux x86-64. GHCR публикует backend для `linux/amd64`. Ориентир для
  ограниченного пилота без PDF — 2–3 vCPU, 4 ГиБ RAM, от 40 ГиБ SSD. Репетиция
  прошла с 3 vCPU и 4 ГиБ, при этом на прогретом пустом стенде backend занимал
  около 342 МиБ, PostgreSQL около 138 МиБ. Нижняя граница CPU и одновременные
  пользовательские нагрузки требуют замеров. По диску учитывайте два образа,
  рост БД/WAL, ограничение Docker-логов и место под зашифрованную копию.
- На выделенном хосте нужны Docker Engine с `image inspect --platform`, Compose
  с `config --hash` и `up --wait --wait-timeout`, Python 3.9+, Bash, GitHub CLI с
  `api --paginate --slurp` и доступом на чтение к Actions runs, jobs и artifacts, `age`, `shasum` и Caddy 2. Разместите checkout с проверенным
  профилем на постоянном пути. Закрепите файлы init SQL, traffic-gate.sh и Caddyfile из этой версии; изменять их может только оператор.
  Доступ к Docker и приватным файлам имеет оператор. Настройте лимит и ротацию
  Docker-логов, синхронизацию времени, обновления ОС и мониторинг заполнения диска.
  Открываются TCP 80/443 и административный SSH с разрешённых адресов.
- Заранее согласуйте, кто обслуживает уже выданные ссылки `/v/…` на apex,
  и какие QR/ссылки ведут в staging. Идентификаторы заведений из независимых
  баз могут совпадать. Переключение общего apex без инвентаризации может
  отправить старую ссылку в другое заведение. В production используется формат
  `/v/<slug>`. Wildcard и staging-поддомены требуют собственного плана.
- Определите Platform Owner, подтвердите ручной биллинг, ограничения загрузок,
  бюджет, off-site хранение и полномочия на восстановление. Профиль HT70,
  staging-бот и серверные файлы staging для этого не нужны.

## Подготовка кандидата

Работайте на будущем выделенном production-хосте из корня проверенного checkout.
Оператор назначает `P` приватным каталогом вне Git с правами 0700, а `RUN`,
`SHA`, `ATTEMPT` берёт из завершённого успешного push CI на main. Команды
ниже предназначены для отдельно разрешённого запуска.

```bash
set -euo pipefail
umask 077
export DOCKER_HOST=unix:///var/run/docker.sock
unset DOCKER_CONTEXT COMPOSE_PROJECT_NAME COMPOSE_FILE
install -d -m 700 "$P"
test ! -e "$P/runtime.env"
install -m 600 deploy/production/runtime.env.example "$P/runtime.env"
gh run download "$RUN" -R koteev-m/hookah_bot \
  -n "ghcr-candidate-${SHA}-${ATTEMPT}" -D "$P/ci-$SHA"
```

Копируйте шаблон только при первом вводе. Заполните `runtime.env` в приватном
редакторе. Каждая из шести величин в hex — независимые 32 случайных байта из
production-хранилища. Выберите и запишите digest официального одобренного
PostgreSQL 17. Для инфраструктурной репетиции оставьте бот выключенным.
Для первого рабочего запуска владелец заранее передаёт отдельный токен
`@hookah_tootah_bot` и свой Telegram ID. Убедитесь, что webhook пуст и других
потребителей нет. Укажите их в приватном runtime с `TELEGRAM_BOT_ENABLED=true`
до `admit`. Шаблон с пустым токеном позволяет проверить инфраструктуру.
Для подписанного входа требуется рабочий токен. Значения
паролей Postgres применяются entrypoint только на пустом томе. Ротация для
существующей БД требует согласованных SQL, runtime и проверки соединения.
Все секреты, включая будущий Telegram token, должны иметь отдельное хранение
вне VPS. Доступ к Compose-плану и Docker inspect равнозначен доступу к секретам.

```bash
profile=(python3 -B scripts/production_profile.py)
plan="$P/release-$SHA.json"
ci="$P/ci-$SHA/candidate.json"
"${profile[@]}" check "$P/runtime.env" "$ci"
"${profile[@]}" admit "$P/runtime.env" "$ci" "$plan"
dc=(docker compose --env-file /dev/null -p hookah_production -f "$plan")
```

`check` валидирует шаблон без внешнего доступа. `admit` проверяет repository,
событие push, ветку main, workflow CI, полный SHA и успешное завершение.
Он сверяет candidate с артефактом publishing job **этой попытки**, immutable
digest, OCI source/revision, linux/amd64, версию PostgreSQL и все SQL в JAR
до V143 включительно и поддержку привязки допуска к экземпляру JVM в JAR.
Образы до появления этой поддержки требуют нового релиза. При включённом боте он сверяет токен вызовом `getMe`.
Приватный Compose-план создаётся атомарно по новому пути. В файл попадают
секреты, поэтому его содержимое следует исключить из терминальных логов,
артефактов CI и Git.

### Сохранение доказательств релиза

После первого успешного `admit` передайте хранителю кандидат и квитанцию из допущенного плана.
Квитанция содержит только repository, workflow, run/attempt, SHA и digest образа.
Сохраняйте именно эти файлы в существующем защищённом хранилище вне VPS. Хранитель
фиксирует SHA-256 принятой квитанции по независимому каналу, как для backup manifest.

```bash
evidence="$P/evidence-$RUN-$ATTEMPT-$SHA.json"
(set -C; python3 -c 'import json,sys; print(json.dumps(json.load(open(sys.argv[1]))["x-hookah-release-evidence"],sort_keys=True))' "$plan" > "$evidence")
shasum -a 256 "$evidence"
```

После истечения срока artifact или потери VPS восстановите квитанцию и candidate у
хранителя. Получите ранее записанный `EVIDENCE_SHA256` отдельно. На том же SHA и
digest повторите `admit` с новым путём вывода:

```bash
"${profile[@]}" admit "$P/runtime.env" "$ci" "$NEW_PLAN" --evidence "$evidence" --evidence-sha256 "$EVIDENCE_SHA256"
```

Admission сверяет кандидат с квитанцией и отдельно читает успешный push main и
успешный шаг `Record verified image sha256:…` в `publish-ghcr` именно этой попытки.
Затем повторяются проверки OCI и содержимого JAR. При удалённом run/job, сменившейся
попытке, утрате квитанции и artifact или недоступном digest потребуется новый
проверенный выпуск. План с секретами хранится отдельно.

## Первая установка и проверка

Перед первой установкой при пустом проекте следующие команды должны завершиться успешно. При существующем томе или контейнерах выясните их происхождение
до запуска. Проверьте и отсутствие занятого порта 18080.

```bash
containers=$(docker ps -a --filter label=com.docker.compose.project=hookah_production --format '{{.Names}}')
volumes=$(docker volume ls --format '{{.Name}}' | awk '/^hookah_production_(pgdata|pdf_ipc)$/')
networks=$(docker network ls --format '{{.Name}}' | awk '/^hookah_production_/')
listeners=$(ss -Hlt 'sport = :18080')
test -z "$containers$volumes$networks$listeners"
```

Владелец согласует окно для apex и старых ссылок. Создайте каталог допуска до
запуска Caddy. Для новой установки он пуст. При существующих решениях остановитесь
для идентификации сервера. Установите production Caddyfile, выполните
`caddy validate --config /etc/caddy/Caddyfile` и запустите системный Caddy.
Разрешите ACME доступ к TCP 80/443, направьте A и обслуживаемую AAAA на этот хост
и дождитесь доверенного сертификата для apex. Запись AAAA на прежний хост
должна быть исправлена владельцем. В этот период Caddy обслуживает maintenance.

```bash
install -d -m 0755 /var/lib/hookah-production/ingress
test -z "$(ls -A /var/lib/hookah-production/ingress)"
traffic=(python3 -B scripts/production_traffic.py)
```

После выпуска сертификата с внешней точки проверьте на каждом опубликованном
адресе TLS без `-k`, HTTP 503 и заголовок `X-Hookah-Maintenance: closed` на
`/miniapp/`. Проверьте тот же результат локально через SNI. До подтверждения
DNS и TLS владельцем допустима только изолированная репетиция с тестовым CA.

```bash
curl --noproxy '*' --resolve hookahtootah.club:443:127.0.0.1 -sS -D - -o /dev/null https://hookahtootah.club/miniapp/
"${dc[@]}" up -d --pull never --wait --wait-timeout 180
"${profile[@]}" running "$plan"
python3 deploy/production/smoke.py "$plan"
"${dc[@]}" exec -T postgres psql -XqAt -v ON_ERROR_STOP=1 -U hookah_app -d hookah_prod \
  < deploy/production/history.sql | "${profile[@]}" history
```

`running` сверяет образы, Compose hashes сервисов плана, том и сетевые привязки.
Smoke ожидает `ok` от `/health` и `/db/health`, `prod` и точный SHA от
`/version`, HTML/JS/CSS под `/miniapp/` и HTTP 401 от гостевого API без сессии.
Smoke читает index.html и полные entry JS/CSS из локального образа по digest
с `--pull never` и отключённой сетью. Он сверяет размер и SHA-256 каждого
ответа с этими байтами, а также MIME и same-origin URL. Проверка history требует 143 успешные записи в порядке установки, с точными
именами и Flyway checksums репозиторных миграций V1–V143.

Для первой в истории production-установки хранитель подтверждает, что ранее действовавшего
production нет. Только тогда используйте `--first-install`. На пустом диске заменяющего VPS
историю определяет владелец по внешним записям. После потери VPS начинайте с
`recovery-begin`; обычный `bind-db` без подтверждённого режима отклоняется.
Первичная привязка выполняется до появления пользователей, заведений и бизнес-данных.
После проверки свежей V143 оператор сверяет кластер, volume и публичный ключ
age с хранителем. Единожды зарегистрируйте БД и получателя в приватном
каталоге всех допущенных планов. Сохраните независимую защищённую копию
`postgres-binding.json`. Замена PostgreSQL-контейнера тоже изменяет привязку.
При расхождении требуется отдельная идентификация БД и решение владельца.
Повторная регистрация во время аварии скрыла бы причину отказа.

```bash
"${profile[@]}" bind-db "$plan" "$RECIPIENT" --first-install
# Только после первичной привязки БД. Подписанный вход создаёт обычную пользовательскую сессию.
python3 -B deploy/production/smoke.py "$plan" --owner-init-data "$P/owner-init-data"
# Завершите браузерную проверку через защищённый туннель и получите разрешение на открытие.
"${traffic[@]}" open "$plan"
```

Для закрытого smoke владелец задаёт production Main Mini App URL в BotFather и запускает
Mini App из Telegram. Свежая подписанная строка `initData` доступна владельцу
в launch fragment WebView даже на странице maintenance. Через приватный канал
сохраните декодированное значение параметра `tgWebAppData` в `$P/owner-init-data`
(0600). Передавайте его только на loopback первого сервера. Не записывайте fragment,
initData и ответ с JWT в логи. Smoke подтверждает закрытый HTTPS до и после реального
`POST /api/auth/telegram`, проверяет ID владельца и выданный токен. После проверки
удалите временный файл учётных данных. При отсутствии свежей подписи открытие отложите.
Для worker в media-плане Compose ожидает healthy, затем `running` проверяет
его фактическую изоляцию. После разрешённого open проверьте публичные HTTPS
health/version и Mini App на устройстве.

Диагностика обновления через `inspect OLD NEW` возвращает ненулевой код для UNKNOWN и отсутствующего backend. Сохраните вывод и выясните причину до следующей операции.

## Backup и проверочное восстановление

Назначьте `POINT` новым путём каталога и `RECIPIENT` публичным age-получателем
независимого хранителя. Секретный ключ восстановления держите у хранителя.
Для backup требуется существующий контейнер backend точного плана. В профиле без медиа он может работать, быть остановлен или иметь статус unhealthy. Для профиля с R2 остановите backend по процедуре ниже. Он проверяет образ,
здоровье и Compose hash PostgreSQL, контейнер, сеть и том, идентификатор кластера,
OID/владельца БД, Flyway V1–V143 и зарегистрированного получателя. При отказе
сохраните привязку и выясните причину. Backup создаёт custom-format pg_dump в потоке через age и перечень SHA-256.
Каталог без готового `SHA256SUMS` неполон. Скопируйте завершённую точку во
внешнее хранилище с независимыми правами, сохраните идентификатор версии и
проверьте считанные обратно байты. Digest PostgreSQL должен происходить из
доверенной конфигурации.

```bash
deploy/production/backup.sh "$plan" "$POINT" "$RECIPIENT"
# На изолированном restore-хосте с предзагруженным образом и тем же инструментарием
deploy/production/restore-test.sh "$POINT" "$AGE_IDENTITY_FILE" "$APPROVED_PG_DIGEST"
```

Restore проверяет SHA-256, расшифровку, всю загрузку архива в одной транзакции,
историю Flyway и `pg_amcheck`. Он поднимает отдельный PostgreSQL с новым
именованным томом, без сети, портов и Docker-логов. Для каждой попытки
оператор использует того же системного пользователя, Docker daemon и постоянный
приватный `${XDG_STATE_HOME:-~/.local/state}/hookah-production-restore`.
Журнал фиксирует daemon, digest и UUID до выделения ресурсов. После обрыва
повторный запуск проверяет имена, метки, подключения и владельца тома, убирает
остатки прошлой попытки и начинает новую. Сообщение об успехе появляется после
проверки удаления контейнера и тома. При неизвестном ресурсе или ошибке удаления
сохраните журнал и ограничьте доступ администраторам до разбора. Защитите диск
restore-хоста шифрованием, поскольку данные в тестовом томе расшифрованы.
По желанию четвёртым аргументом передаётся доверенный SQL-файл с проверками,
которые завершаются ошибкой при потере контрольных данных. Реальную копию
проверяет независимый оператор в изолированной среде. Возврат данных в рабочую
БД требует отдельного решения о точке восстановления и допустимой потере.

Этот дамп покрывает одну БД приложения. Роль пересоздаётся штатным init SQL,
секреты, образ, DNS/TLS, конфигурация бота и внешние медиа требуют отдельного
хранения. До реальных данных владелец должен обеспечить и подтвердить
production-процедуру по Policy B. В действующей политике предусмотрены снимок
каждые 6 ч, квалификация за 2 ч, контроль каждые 5 мин, 7 дней хранения и
минимум две пригодные точки. Локальная репетиция подтверждает операции
backup/restore только на синтетических данных. [Политика восстановления](DEPLOYMENT_RUNBOOK.md#policy-b-disaster-recovery--ht-ops-04--ap-01).

## Обновление действующей версии

Один оператор ведёт обновление из постоянного проверенного checkout. `OLD` и
`NEW` — приватные планы в каталоге с исходным `postgres-binding.json`.
Сохраните SHA и immutable digest обоих образов. `admit --previous` сверяет
происхождение нового коммита, зелёный main CI и разрешает изменить только
backend digest и revision. План сохраняет обе пары SHA/digest и версию схемы.
При обновлении с V142 Flyway применяет один файл `V143__billing_courtesy_operation.sql`
с checksum `1900727557`. Он добавляет ключ и результат операции начисления льготы.
После запуска проверьте текущую версию 143, 143 успешные записи истории, 0 pending
и 0 failed. Контракт CI сверяет имя и SHA-256 каждого файла после исторической V126.
На staging с V142 изменение вступит в силу только при отдельном запуске нового backend
на его БД. Исторический cutover для V126 продолжает отклонять более новые схемы.
Изменение схемы выше V143, runtime, сети, образа
PostgreSQL или включение бота требует отдельного решения.

```bash
traffic=(python3 -B scripts/production_traffic.py)
"${profile[@]}" running "$OLD"
"${profile[@]}" admit "$P/runtime.env" "$NEW_CANDIDATE" "$NEW" --previous "$OLD"
"${traffic[@]}" close "$OLD"
deploy/production/backup.sh "$OLD" "$POINT" "$RECIPIENT"
```

`close` убирает постоянный маркер, останавливает процесс OLD вместе с polling
и подтверждает по HTTPS через loopback ответ 503 с заголовком
`X-Hookah-Maintenance: closed`. В media-профиле backend остаётся остановленным даже при неисправном PDF worker.
Для обычного пилота без медиа команда снова запускает OLD в закрытом режиме и
проверяет его готовность на `127.0.0.1:18080`. Для открытия любого media-плана
требуется штатный допуск работающего worker.
При замене процесса в `stage` эти endpoints кратко недоступны; PostgreSQL
проверяется напрямую. Клиентский ingress и polling остаются закрыты при
перезапуске контейнера или ОС.

Получите результат restore-test для этой точки из независимого хранилища.
Запишите идентификатор копии. Только затем продолжайте.

```bash
"${traffic[@]}" stage "$OLD" "$NEW"
"${traffic[@]}" inspect "$OLD" "$NEW"
python3 deploy/production/smoke.py "$NEW"
```

Пока ingress закрыт, откройте `/miniapp/` в Chromium через защищённый туннель
на loopback оператора. Проверьте отрисовку содержимого внутри `#app`, загрузку
стилей и отсутствие ошибок модуля. HTTP smoke отдельно проверяет статус,
same-origin URL, MIME и содержимое entry JS/CSS. Разрешите трафик только после
успеха этих проверок и решения оператора.

```bash
"${traffic[@]}" open "$NEW"
"${traffic[@]}" inspect "$OLD" "$NEW"
```

`open` проверяет закрытый HTTPS, образы, привязку PostgreSQL и V1–V143,
затем выполняет loopback smoke на окончательной JVM. `/version` возвращает
SHA, уникальный для запуска `instance` и состояние polling. Пока вход закрыт,
проверенная JVM обслуживает административные запросы. Замены процесса
при открытии нет.

Операторская команда атомарно сохраняет в `activate` пару SHA и instance.
Для включённого бота тот же процесс проверяет отсутствие webhook и приобретает
единственную аренду polling. До публикации файла `open` worker читает с timeout 0
без offset. Полученные updates остаются в очереди Telegram. Роутер, outbox и
настройка меню ожидают открытия. Для `running` нужен успешный ответ getUpdates
от этого worker.
Worker делает до трёх попыток с backoff в серии. Без подтверждения дольше long-poll timeout плюс 15 секунд
готовность теряется. В репетиции с TELEGRAM_BOT_ENABLED=false ожидается disabled и пустые реквизиты. Новый процесс не может использовать прежнюю пару.
После подтверждения `running` (или `disabled` для выключенного бота), повторных
проверок Flyway, контейнеров, assets и instance команда сохраняет эту же пару в
`open`. Caddy добавляет служебный заголовок к публичному запросу. Backend
проверяет оба решения и состояние poller перед обработкой такого запроса.
Перед каждым публичным запросом JVM проверяет соединение с PostgreSQL. Одновременные
запросы разделяют выполняющуюся проверку. При открытом входе выполняется также один
фоновый контроль в секунду. Отказ БД или утрата готовности polling отзывает допуск
этой JVM. Публичный HTTP отвечает 503, в том числе после возвращения БД. Для диагностики
используйте loopback /health, /db/health и /version. После устранения причины выполните
явный close для текущего плана, проверьте новую JVM, затем open. Сохранённый маркер
после SIGKILL или reboot сам по себе не открывает вход.

При несовпадении instance публичные операции закрыты. Не публикуйте loopback
порт backend. После допуска проверьте публичные HTTPS health/version/Mini App
и, в разрешённом окне, вход через настоящий Telegram.

**После обрыва сессии** выполните `"${traffic[@]}" inspect "$OLD" "$NEW"`.
Инспекция проверяет привязку PostgreSQL и показывает фактическую версию,
состояние backend и оба решения оператора. Сверьте их с loopback `/version`.

| Наблюдение | Действие оператора |
| --- | --- |
| CLOSED, NEW stopped | Запустите `"${traffic[@]}" resume "$OLD" "$NEW"`. Команда повторно проверит DB binding и точный контейнер NEW, запустит его по ID, сверит Flyway, health, version и assets. PostgreSQL продолжит работать. Выполните браузерный smoke, затем явно вызовите `open "$NEW"`. |
| CLOSED, NEW running | Повторите loopback smoke по плану NEW и браузерную проверку. После SIGKILL во время resume контейнер уже может работать. После SIGKILL до публикации open может сохраниться разрешение на пробное чтение. Команды и outbox остаются закрыты. Повторный явный open сверит тот же процесс и его готовность. |
| CLOSED, OLD running | Проверьте drain, локальный health, состояние polling и квалификацию backup перед оставшимся шагом обновления. |
| CLOSED, OLD stopped после отказа NEW worker | Backend ещё принадлежит OLD. При совместимой схеме выполните процедуру возврата ниже, начиная с `rollback "$OLD" "$NEW"`. |
| Сохранён open | Сверьте SHA и instance с живым ответом через HTTPS. Если JVM перезапустилась, обёртка ждёт снятия прежнего решения. Выполните close для идентифицированного плана и повторите квалификацию. |
| Неизвестный контейнер, изменённые digest, том, сеть или cluster ID | Сохраняйте ingress закрытым. Зафиксируйте исходную привязку, оба плана и диагностику. Замена PostgreSQL, повторный bind, rollback или restore требуют отдельного решения. |

При ошибке запуска polling сохраните закрытый HTTP, устраните причину ошибки
бота, затем выполните close для подтверждённого плана и проверьте новую JVM.
Маркер вручную не создаётся. Вне Git сохраняется исходный защищённый каталог
оператора, включая привязку БД и допущенные планы.

### Возврат прежнего релиза после неуспешного обновления

Для media-плана оператор подтверждает, что NEW не принимал прикладную запись и
что обе версии совместимы с текущими данными и точной Flyway history. Сначала
выполните `"${traffic[@]}" inspect "$OLD" "$NEW"`. Для работающего NEW выполните
`"${traffic[@]}" close "$NEW"`. Если уже остановлен OLD или NEW, убедитесь,
что результат инспекции показывает CLOSED и activation none. Далее:

```bash
"${traffic[@]}" rollback "$OLD" "$NEW"
"${profile[@]}" running "$OLD"
python3 -B deploy/production/smoke.py "$OLD"
# После закрытого smoke и решения оператора:
"${traffic[@]}" open "$OLD"
```

Команда проверяет исходную привязку PostgreSQL, допущенный прямой переход,
одинаковую версию схемы и точный остановленный backend. Неисправный NEW worker
может уже занимать место прежнего, даже когда backend ещё принадлежит OLD.
Rollback идентифицирует worker по полному ID, плану Compose, IPC-тому и digest,
останавливает подтверждённый NEW worker по ID, ожидает healthy прежнего worker
и запускает OLD backend. PostgreSQL, готовность backend и закрытый HTTPS должны
пройти проверку. При отказе сохраните maintenance и выполните `inspect` повторно
перед выбором следующего действия. При неизвестном контейнере, несовместимой
семантике записанных данных или миграции, включая V142 → V143, сохраняйте
maintenance. Выберите forward-fix либо восстановление отдельной проверенной
точки с решением владельца о судьбе последующих записей.

## Границы пилота

- `BILLING_PROVIDER=fake` поддерживает счета, ручную отметку оплаты Platform
  Owner и льготные дни с основанием. Он не списывает деньги, не даёт рабочую
  платёжную ссылку и не подтверждает банковский расчёт. Автоматический биллинг в пилоте **OFF**. Итоговый Compose задаёт
  `BILLING_SUBSCRIPTION_INTERVAL_SECONDS=0`. Задача не готовит счета и
  напоминания, не переводит заведения в `PAST_DUE` и `SUSPENDED_BY_PLATFORM`.
  Владелец ведёт календарь окончания trial и льгот и явно принимает решение
  о продлении на конкретный срок или о статусе заведения.
  За период с ценой 0 ₽ платёжный счёт не создаётся. Более ранние платные
  обязательства сохраняются. В Venue и Platform откройте «Неоплаченные счета».
  У каждого счёта есть свой ID, сумма, срок и статус. «Открыт» допускает будущий
  срок оплаты, «Просрочен» соответствует `PAST_DUE`. Разверните нужную запись
  по номеру. Ручная отметка оплаты применяется только к выбранному счёту.
  Список показывает до 50 неоплаченных счетов за раз в порядке ID, начиная
  со старых. При наличии продолжения нажмите «Следующие неоплаченные счета».
  Ошибка загрузки требует повторной проверки. История последних 50 счетов
  и совместимое поле API `payableInvoice` сохраняют прежнее значение.
  Дату следующего платежа показывает только явное поле ответа сервера. Бесплатный период сам по себе не меняет статус
  подписки. Для гостевых операций опубликованного заведения resolver допускает
  TRIAL, ACTIVE и PAST_DUE. UNKNOWN, CANCELED и приостановка закрывают эти
  операции. Просмотр публичной ссылки при отсутствующей строке подписки имеет
  отдельный read-only контракт. На части гостевых маршрутов сохраняется
  существующая ленивая инициализация TRIAL. Перед приглашением гостей задайте
  явный статус и дату пересмотра. Серверные проверки прав действуют.
  Реальный эквайринг,
  Stars и автосписания выходят за пределы пилота. [Биллинг и подписки](PLATFORM_COCKPIT.md#billing--subscriptions--invoices).
- Прямые загрузки подключаются параметром `PRODUCTION_MEDIA_ENABLED` при допуске профиля.
  Порядок настройки, холодной копии и восстановления приведён ниже.

### Приватные фото, планы залов и PDF

Для этого профиля выбран приватный bucket `hookah-tootah-media-production-eu` в юрисдикции EU.
В Cloudflare оператор отдельно создаёт bucket и проверяет его фактическую юрисдикцию,
отключает публичный доступ через r2.dev и custom domains. Выпустите отдельные S3-ключи
с Object Read & Write только для этого bucket. Ограничение прав и приватность проверяются
в настройках провайдера: по строке ключа они не определяются. В приватном runtime задайте
`PRODUCTION_MEDIA_ENABLED=true` и шесть полей `STAFF_PHOTOS_R2_*` из примера.
Регион — `auto`, юрисдикция — `eu`, endpoint — `https://<32 hex account id>.eu.r2.cloudflarestorage.com`.
Проверьте источник account ID независимо. Предоставьте ключам резервное хранение у оператора.
Файл конфигурации, допущенный план и вывод docker inspect содержат секреты.

Для новой установки применяются обычные `check`, `admit` и закрытая первая установка.
Для уже установленного пилота сначала обновите образ штатным способом до релиза с поддержкой
production media. На том же проверенном digest подготовьте отдельный приватный план через
`admit` с новым runtime. Сверьте, что изменились только поля медиа, IPC-том и worker.
Закройте прежний план. Запустите worker и backend из нового плана за закрытым gate.
Обычные последующие обновления снова используют `--previous`.
Дождитесь healthy worker и выполните `running`. Проверьте отсутствие чужих ключей и
публичной выдачи, загрузку, замену, просмотр и удаление синтетических файлов от разрешённых
ролей. Переключение DNS и открытие трафика требуют отдельного решения.

Профиль использует backend для чтения и записи объектов по существующим RBAC и правилам
видимости. В PostgreSQL остаются права, метаданные, согласия и журналы удаления.
На Linux требуются cgroup v2 и действующий seccomp. Worker и backend используют один digest
и выделенный том `hookah_production_pdf_ipc` с Unix socket. Worker работает без сети и
runtime-секретов, с read-only rootfs, UID/GID 10001, no-new-privileges, cap_drop ALL,
384 МиБ RAM, нулевым swap, одним CPU и лимитом 64 PID. На systemd проверяется также
MemorySwapMax у scope. После старта отказ worker закрывает приём новых PDF. Уже сохранённые
файлы и изображения обслуживаются через backend при доступном хранилище.

### Копия и восстановление production media

Для чтения объектов на backup-хосте нужен Python с boto3/botocore, для шифрования —
тот же зарегистрированный age-получатель. Согласуйте периодичность, срок удаления старых
копий, допустимую потерю записей, время простоя и ответственного за независимое хранение.
Закройте traffic gate командой `close` допущенного media-плана. Она остановит его backend. Исключите
все сторонние записи в PostgreSQL и bucket до завершения копирования. Worker и PostgreSQL
остаются запущенными. Backup удерживает тот же flock, что и операции трафика, сверяет
фактические флаги R2/PDF и идентичность контейнера с планом до и после копирования.
Опись и `pg_dump --snapshot` читают один экспортированный снимок PostgreSQL.
При несовпадении профиля, привязки или контрольной суммы итоговый `SHA256SUMS` не появляется.

```bash
backup_backend=$("${dc[@]}" ps --no-trunc -q backend)
"${traffic[@]}" close "$plan"
deploy/production/backup.sh "$plan" "$POINT" "$RECIPIENT"
# После успешной холодной копии возобновите тот же релиз и тот же контейнер.
"${traffic[@]}" start-closed "$plan" "$backup_backend"
"${traffic[@]}" open "$plan"
```

`start-closed` проверяет закрытый HTTPS, первоначальную привязку PostgreSQL и
ID остановленного backend, запускает его по этому ID и повторно сверяет контейнер,
PostgreSQL, PDF worker и готовность JVM/статических файлов. Только `open` выдаёт
допуск трафика. При ошибке сохраните закрытый трафик и проверьте указанный компонент.
Если команда оборвалась при старте и backend уже работает, сверьте его полный ID с
`$backup_backend`. Только при совпадении выполните
`"${profile[@]}" running "$plan"`, loopback smoke и явный `open "$plan"`.
После отдельной холодной точки `--metadata-only` используется тот же порядок.

Полная точка содержит зашифрованные `database.dump.age` и `media.tar.age`. Каждая новая
media-точка также содержит `source-coordinate` с system identifier PostgreSQL, OID БД,
timeline и позицией WAL при закрытой записи. Содержимое всех частей связано файлом
`SHA256SUMS`. Передайте точку в существующее независимое закрытое хранилище. Хранитель
фиксирует версию копии и SHA-256 самого `SHA256SUMS` в независимой доверенной записи
после сверки принятых данных. Для последующего восстановления он передаёт сохранённый
хеш отдельным доверенным путём. Хеш с потерянного VPS или из скачанного каталога
сам по себе происхождения копии не удостоверяет.

Если исходная БД ещё доступна, после остановки всех писателей снимите более позднюю
точку метаданных, даже если R2 недоступен. Подготовьте для неё отдельную запись у хранителя.

```bash
deploy/production/backup.sh "$plan" "$METADATA_POINT" "$RECIPIENT" --metadata-only
```

**Восстановление на чистом хосте.** Подготовьте закрытый Linux Docker-хост с зашифрованным
диском, доступом только администратора, предзагруженным одобренным digest PostgreSQL 17
linux/amd64, age и этой версией операторских скриптов. Получите закрытый age-ключ отдельно
от копий. Перенесите обе точки и получите от хранителя соответствующие хеши. Свободного
места должно хватить для восстановления дампов, индексов и отобранных байтов. Запускайте
под постоянной учётной записью на одном Docker daemon.

```bash
umask 077
deploy/production/restore-test.sh "$POINT" "$AGE_IDENTITY_FILE" "$APPROVED_PG_DIGEST" \
  --point-sha256 "$POINT_RECEIPT_SHA256" --metadata-point "$METADATA_POINT" \
  --metadata-sha256 "$METADATA_RECEIPT_SHA256" --keep-quarantine
```

Инструмент проверяет оба манифеста, один источник, одну timeline и возрастание LSN.
Он восстанавливает индекс старой копии во временную БД, затем загружает более поздний
дамп в рабочую `hookah_prod`, сохраняя её права, указатели и tombstones. Размер и SHA-256
сверяются для каждого архивного объекта. В `hookah_recovery.objects` попадают только
совпадающие ключи с теми же байтами и признаками видимости. Изменённые права, скрытие,
удаление и замена исключают старый объект. Появившиеся позже ключи представлены
метаданными без байтов и учитываются в `newer_without_bytes`. Для них нужна более
свежая копия байтов. Конфликт содержимого одного ключа, неполный архив, повреждение
age или ошибка проверки сохранённых байтов прерывают всю попытку.

При единственной доступной полной точке опустите оба параметра метаданных. Помощник
восстановит состояние на дату этой копии в том же карантине. Без `--keep-quarantine`
выполняется временная проверка с удалением ресурсов. Старые точки без координаты
допустимы для одноточечного восстановления. При успехе постоянного восстановления
команда печатает точное имя контейнера и путь к квитанции в приватном state-каталоге.
Контейнер использует именованный том, Unix socket и отключённую сеть. Приложение
не имеет LOGIN и доступа к схеме объектов. Пример проверки администратором после
перезагрузки хоста, где `RECOVERED` — имя контейнера из результата:

```bash
docker start "$RECOVERED"
docker exec "$RECOVERED" psql -X -U postgres -d hookah_prod -c 'SELECT count(*) FROM hookah_recovery.objects'
```

### Потерян один объект R2, действующая PostgreSQL сохранилась

Оператор подтверждает непрерывность исходной БД, отсутствие restore и сторонних
писателей. Запомните полный ID работающего backend, выполните `close` как для
холодного backup. Получите из доверенной полной копии байты нужного ключа.
На закрытом носителе проверьте независимый SHA-256 манифеста и его файлы,
затем извлеките ровно этот объект (Bash с `set -euo pipefail`, umask 077):

```bash
test "$(shasum -a 256 "$POINT/SHA256SUMS" | cut -d' ' -f1)" = "$POINT_SHA256"
(cd "$POINT" && shasum -a 256 -c SHA256SUMS)
age -d -i "$IDENTITY" "$POINT/media.tar.age" | tar -xO -f - -- "$OBJECT_KEY" > "$P/repair-bytes"
python3 -B deploy/production/media_backup.py repair-object "$plan" "$RECIPIENT" "$OBJECT_KEY" "$P/repair-bytes"
```

Repair удерживает блокировку оператора и SHARE locks на таблицах inventory до
проверки результата. Требуются исходная привязка БД, закрытый HTTPS, точная
остановленная media-установка и текущая допустимая запись. SHA-256 и размер
сверяются с PostgreSQL перед условным созданием в приватном bucket и после
обратного чтения. Существующий ключ защищён `If-None-Match: *`. Отозванная
видимость, tombstone или замена ключа блокируют операцию. Права и строки БД
сохраняются. При неоднозначном ответе R2 оставьте сервис закрытым, проверьте
уже созданный объект по текущему checksum. После успешной сверки удалите
временную расшифровку и используйте `start-closed` и `open` для того же ID.
**Скрытое вложение информационного раздела, включая фото- и PDF-меню.**
При сохранной действующей БД и действующих полномочиях OWNER или MANAGER своего
заведения откройте скрытое вложение в режиме управления. Если сервис был остановлен,
сначала верните тот же допущенный backend по штатной процедуре. Проверьте пометку
скрытого вложения и его раздел. Выберите «Заменить это вложение» и передайте
проверенную копию нужного JPEG, PNG или PDF. Mini App отправляет текущий ID в
`X-Replaces-Media`, ревизию в `X-Media-Revision` и `Idempotency-Key`.
При конфликте ревизий перечитайте карточку. Замена сохраняет позицию и видимость,
создаёт новый приватный объект и закрывает старый ID. Проверьте байты в предпросмотре
управления и гостевой ответ 404 для обоих ID. Публикация для этой операции не требуется.

Для плана зала загрузите новый JPEG/PNG в том же зале и проверьте приватный
предпросмотр. Остановитесь до команды применения `PLAN`: новый ID остаётся
недоступным гостю даже при включённом выборе столов. Применение плана отдельно
изменяет привязку и сбрасывает разметку.

Для фото сотрудника доступ зависит и от карточки, и от состояния самого фото.
При скрытой карточке штатная загрузка сохраняет закрытый гостевой доступ.
Если причина запрета — только состояние фото `HIDDEN` в видимой карточке,
обычная замена делает новое фото текущим и одобренным. Оставьте такой объект
закрытым: автоматический возврат прежнего ключа или видимости не предусмотрен.
При утраченной актуальной БД применяется процедура ниже.

### Катастрофическая потеря primary и последнего состояния прав

**Архив остаётся закрытым навсегда.** Даже если последний доступный дамп считает
фотографию опубликованной, а прежнего сотрудника владельцем, восстановленный контейнер
остаётся без сети, с ролью приложения NOLOGIN и отдельным закрытым хранилищем байтов.
Такой результат можно исследовать через локальный административный socket. Никогда
не подключайте его том к serving PostgreSQL, не выдавайте LOGIN и не переносите
дамп, каталог объектов, старые R2-ключи объектов, Telegram file_id или ссылки в
рабочие реестры. Подключённые к сети backend, бот, предпросмотр и фоновые обработчики
не получают доступа к архиву. Порядок копий не подтверждает последующие отзывы.
Политика распространяется и на восстановление из единственной старой точки.

**Подготовьте замену** на одном штатном production-стеке. Изолированную копию можно
держать остановленной между административными проверками. Дополнительный постоянный
сервис или синхронная реплика не нужны. Сначала оградите прежний VPS и его писателей,
отзовите скомпрометированные ключи и сохраните доступ к зашифрованным копиям по правилам
хранителя. Подтвердите личность Platform Owner и владельцев заведений через действующие
доверенные контакты вне восстановленной БД. Подготовьте новые session JWT, пароли,
peppers, входные токены и приватные bucket-scoped credentials. Перепроверьте привязку
бота, отключите scheduler и автоматический billing. Сохраняйте DNS и ingress закрытыми.
Оператор, Docker daemon и хост в этой процедуре доверенные.

1. Подготовьте одобренный release с поддержкой `recovery-hold`, свежий приватный план
   и пустой production-том по разделу первой установки. Установите Caddyfile из этого
   release. До создания backend запустите **только PostgreSQL**. Проверьте, что
   `open` и `activate` отсутствуют. Возьмите у хранителя SHA-256 манифеста той точки,
   из которой сверяются бизнес-данные (при двух точках это дамп метаданных).

```bash
"${dc[@]}" up -d --pull never --no-deps postgres
# Дождитесь healthy у postgres. RECOVERY_POINT_SHA256 поступает от хранителя.
"${traffic[@]}" recovery-begin "$plan" "$RECOVERY_POINT_SHA256"
"${dc[@]}" up -d --pull never
# После миграций до V143, до ввода данных:
"${profile[@]}" bind-db "$plan" "$RECIPIENT"
```

   Команда фиксирует запрет и проверяет пустую схему, digest образа и фактические
   container, volume, cluster ID и OID новой БД. Первая привязка заполненного
   дампа через обычный `bind-db` отклоняется. Во время удержания прикладные пути backend, включая loopback,
   отвечают 503. Для внутренней проверки доступны только GET здоровья, версии и
   статических файлов Mini App с заголовком `X-Hookah-Recovery-Probe: 1`. Маркер
   публичного ingress исключает эту возможность через Caddy. На восстановленной установке фоновые
   операции БД (очистка медиа и сессий, обработка броней, напоминания) ожидают
   допуск нового процесса. Polling и выдача закрыты. Состояние
   миграций проверяйте непосредственно SQL в ожидаемой БД. Обычные `open`,
   `stage` и `resume` не снимают запрет.

2. На закрытой установке отдельно сверяйте архив с независимыми деловыми записями
   и с целевой БД. Зафиксируйте идентичность и область полномочий каждого будущего
   владельца, сопоставление пользователей, состав и статусы заказов/табов, броней
   и мест, суммы счетов, платежи/возвраты, подписки, очереди и внешние эффекты.
   Согласуйте только проверенные бизнес-факты для новой БД. Сохраняйте исходную
   историю и ссылки на доказательства у владельца. Копирование схем/таблиц из дампа,
   воспроизведение сообщений, платежей или бронирований ради совпадения счётчиков,
   а также признание пустой БД восстановленной историей недопустимы.
   Универсального импортера бизнес-истории этот профиль не предоставляет. Если
   для реальных записей нет согласованного способа переноса с сохранением истории
   или остались расхождения, оставьте запрет и передайте их владельцу для отдельной
   процедуры восстановления. Происхождение прав не выводится из роли в архиве.

3. Завершите записи и оградите всех внешних писателей. К моменту приёмки в
   целевой БД отсутствуют материалы, публикации, членства, приглашения, ссылки
   на сотрудников, активные привязки чатов и заготовленные задания рассылки.
   Активных посещений стола, личных/общих счетов и приглашений также быть не должно.
   Завершение незакрытых финансовых обязательств требует отдельной сверки. После неё
   в рабочей БД можно сохранить закрытые счета, заказы, их состав и финансовые факты.
   Состав прежних участников и привязки владельцев счетов сохраняются в архиве.
   В рабочей копии оставьте `tab.owner_user_id` пустым и не переносите `tab_member`.
   Владелец личного счёта участвует в определении гостя посещения, а членство даёт
   доступ к контексту заказа в поддержке даже после закрытия счёта.
   Проверьте отдельно отсутствие старых ссылок/вложений в произвольном тексте и
   импортированных пользовательских данных. Сверьте идентичность плана и БД.
   На работающей JVM под удержанием получите позицию **целевой** БД:

```bash
shasum -a 256 "$plan"
"${dc[@]}" exec -T postgres psql -XqAtw -v ON_ERROR_STOP=1 -U postgres -d hookah_prod \
  < deploy/production/recovery-admission.sql
```

   Пустой результат блокирует приёмку. Проверьте причину на целевой БД, сохраните
   архив. В приватном файле `$REVIEW` (0600) владелец через доверенного оператора
   фиксирует решение следующей формы. Значения evidence — SHA-256 фактических
   материалов сверки соответствующего раздела; один отчёт может покрывать несколько
   разделов. Укажите исходный manifest, cluster ID и OID из `recovery-begin`,
   SHA-256 точного плана, полученный LSN и одноразовый `challenge` из
   `recovery-begin` или текущего файла `/var/lib/hookah-production/ingress/recovery-hold`. Передайте утверждённый SHA-256 самого
   файла оператору по проверенному каналу. Скрипт сверяет привязки, технические
   условия и хеш. Содержание отчётов и полномочия подписанта проверяет оператор.

```json
{
  "decision": "ACCEPT_RECONCILED_REPLACEMENT",
  "challenge": "<64 hex из текущего recovery-hold>",
  "source_manifest": "<SHA-256 манифеста точки>",
  "plan_sha256": "<SHA-256 плана>",
  "cluster_and_db": "<system_identifier>|<OID>",
  "wal_lsn": "<LSN целевой БД>",
  "evidence": {
    "owners_and_grants": "<SHA-256>", "users": "<SHA-256>", "orders": "<SHA-256>",
    "bookings": "<SHA-256>", "billing": "<SHA-256>", "pending_effects": "<SHA-256>"
  }
}
```

4. Сохраняйте запрет на запись до завершения первого открытия. Владелец
   подтверждает текущий challenge, план, БД и её позицию. Оператор выполняет:

```bash
"${traffic[@]}" recovery-accept "$plan" "$REVIEW" "$APPROVED_REVIEW_SHA256"
"${traffic[@]}" open "$plan"
```

   Первый `open` однократно расходует решение владельца. Под действующим
   `recovery-hold` он проверяет PostgreSQL, LSN, PDF worker, образ, файлы Mini App и
   экземпляр JVM. Затем подготавливает `activate` и `open`, подтверждает, что Caddy
   всё ещё возвращает 503, и повторяет проверки идентичности, готовности и LSN.
   Сначала скрипт сохраняет приватную квитанцию `recovery-accepted` на диск.
   Только последнее атомарное снятие `recovery-hold` разрешает запуск обработчиков. Доступ к прикладным API открывается для той же JVM
   после успешного рабочего polling, когда бот включён.

   Для включённого бота проверка вызывает `getWebhookInfo` и `getUpdates` без offset
   с timeout 0. Она требует выключенный webhook и пустую очередь. Она не подтверждает
   updates, не передаёт их роутеру и не отправляет уведомлений. Последнее подтверждённое
   пустое чтение задаёт границу: поступившие после него updates обрабатываются после
   допуска. Повторно доставленный update сверяется со штатным PostgreSQL-реестром
   `telegram_processed_updates` до выполнения команды. Сохраняйте единственного
   потребителя бота и ограждение прежнего VPS на всём интервале.

   Если обнаружены накопленные updates, открытие останавливается. Владелец отдельно
   выбирает контролируемую сверку и обработку ожидающих команд либо явно разрешает их
   списание. Эта процедура не выполняет ни одно из этих действий. Учитывайте срок
   хранения очереди у Telegram при выборе. Как только проверенный `/version` сообщает
   backlog, операторская команда сохраняет одноразовый challenge в `telegram-backlog`.
   Ошибка последующей загрузки Mini App, пустое повторное чтение и рестарт сохраняют
   требование решения. После фактической сверки хранитель передаёт
   digest приватного JSON с `decision=TELEGRAM_BACKLOG_RECONCILED`, этим `challenge`,
   `source_manifest`, `cluster_and_db` из квитанции и `evidence_sha256` материалов
   сверки. При закрытых билетах выполните
   `recovery-telegram-reviewed "$plan" "$REVIEW" "$REVIEW_SHA256"` через traffic-скрипт.
   Команда снимает только инцидент. Следующий допуск вновь требует пустой очереди;
   новый backlog потребует отдельной сверки.

   При сбое до финального снятия удержания, включая SIGKILL, `recovery-hold` продолжает
   блокировать оба билета. Проверьте наличие маркера и состояние экземпляра. Если
   остались подготовленные билеты, зафиксируйте ID командой `"${dc[@]}" ps --no-trunc -aq backend`.
   Выполните `close "$plan"`, затем `start-closed "$plan" "$backend_id"` с этим ID
   через тот же traffic-скрипт. Перед новой попыткой получите новый challenge из
   `recovery-hold`, заново проверьте LSN и запросите новый подтверждённый digest
   решения. Если уже существует `recovery-accepted` без удержания, переход завершился;
   используйте обычный порядок закрытия и допуска этой установки. Сохраняйте файлы
   решений. Старые билеты привязаны к прежней JVM.

   Если recovery принят с выключенным ботом, квитанция сохраняет обязанность
   проверить очередь при первом включении. Закройте прежний runtime, допустите
   план с токеном на том же digest и запустите его закрытым. Первый `open`
   повторяет проверку очереди без offset. Новый процесс и обычный повторный
   запуск видят тот же запрет до фиксации `telegram-recovery-cleared`.
   После фиксации команда ждёт успешный рабочий poll и проверяет через HTTPS
   точные SHA/instance/polling и 401 гостевого API. При ошибке после принятия
   решения команда отзывает билеты трафика и сообщает о совершённом переходе.
   Остановите точный backend, проверьте журнал обработанных updates и outbox;
   уже совершённые действия могут потребовать сверки. После SIGKILL проверьте
   наличие hold, receipt, clearance и фактический HTTPS до повторных действий.

   PostgreSQL может продвинуть WAL служебной записью. Значение LSN само по себе
   не позволяет отличить её от бизнес-изменения. При расхождении сохраните hold,
   закройте оставшиеся билеты, верните точный backend через `start-closed`,
   прочитайте текущий challenge, повторите запрос `recovery-admission.sql` и сверку
   шести областей. Владелец утверждает файл с новым LSN и challenge. Выполните
   `recovery-accept` и сразу `open` в том же закрытом окне.

5. После допуска выдайте новые полномочия только заново проверенным людям через
   штатный Platform/Venue onboarding. Начинайте с закрытой карточки или скрытого
   раздела. Загрузите новые JPEG/PNG/PDF с исходного, разрешённого владельцем
   файла: приложение создаст новые записи, UUID и ключи. Для фото сотрудника
   перепроверьте профиль, согласие и видимость команды; для меню явно откройте
   раздел; для зала привяжите новый план и включите гостевой выбор. Проверьте
   гостевой просмотр после явной публикации и отказ по прежним ссылкам, включая
   менеджерский предпросмотр. Обычный авторизованный предпросмотр относится
   только к новым материалам. Регистры, разрешения и JWT из архива остаются
   непригодными для работы. Существующие приватные байты в R2 не являются
   публикацией; backend ищет объект через запись обслуживающей БД.

### Ручные льготы и оплата в пилоте

Для POST /api/platform/venues/{venueId}/billing/courtesy-days обязательны роль Platform Owner,
поля days и reason и заголовок Idempotency-Key с UUID. До отправки Mini App сохраняет ключ
операции в текущей сессии пользователя. Повтор возвращает первоначальный обзор, включая срок
льготы. Новый запрос после подтверждения получает новый UUID. При 428 обновите Mini App.
При 409 сверьте действие и его параметры. Уникальный ключ, корректировка, изменение статуса
и аудит фиксируются в одной транзакции. Клиентам предыдущих версий требуется обновление.

Фактическая оплата до даты basePaidThrough и льгота до courtesyUntil отображаются отдельно.
Исторический неоплаченный счёт доступен независимо от первых 50 строк истории и цены
нового периода. Настройки сохранённого бесплатного тарифа допускают изменение даты.
Явно заданные цены в форме изменения настроек по прежнему контракту должны быть положительными.
Платёж по старому периоду сохраняется в учёте. Он не снимает административную блокировку.

### Восстановление при административной блокировке подписки

В Platform откройте карточку заведения, обновите биллинг и проверьте основание доступа.
Для статуса `suspended_by_platform` введите обоснование и выберите «Снять блокировку подписки».
В отдельном диалоге подтвердите открытие гостевого доступа для опубликованного заведения.
Публикация, счета, платежи и история льгот сохраняют прежние значения.

Platform Owner вызывает `POST /api/platform/venues/{venueId}/billing/resume-subscription`
с полями `reason` и `expectedUpdatedAt`. Второе поле передаётся без преобразования из
`lifecycleUpdatedAt` последнего ответа `GET /api/platform/venues/{venueId}/billing`.
Сервер блокирует строку подписки в PostgreSQL и сверяет версию, подтверждённую владельцем.
При одновременной записи возврата он дожидается её исхода и повторно читает платёжные данные.
Успешный ответ содержит обновлённый billing overview. Запись аудита
`BILLING_SUBSCRIPTION_RESUMED` сохраняет исполнителя, причину, основание и переход статуса.

| Записи на момент подтверждения | Результат |
| --- | --- |
| Сегодня входит в период оплаченного счёта. Есть соответствующий успешный платёж той же суммы, валюты и провайдера, без зарегистрированного возврата | `ACTIVE` |
| Сегодня входит в предоставленные льготные дни, начиная со дня после `previous_paid_through` и по `new_paid_through` включительно. Начисление подтверждено его аудитом | `ACTIVE` |
| Время окончания действующего trial ещё не наступило | `TRIAL` |
| Только цена 0 ₽, старый платёж, будущая или истёкшая льгота | `409`, административная блокировка сохраняется |

В пилоте нет отдельного оформляемого права бесплатного доступа. Для его введения владельцу
потребуется определить срок, основание и способ отзыва. До этого цена 0 ₽ сама по себе даёт
`409`. Дату окончания trial или льготы оператор контролирует вручную, пока scheduler выключен.

При `409` обновите карточку. Повтор после успеха и запрос для прежней блокировки
не создают второго перехода или аудита. При сетевом сбое сначала перечитайте статус.
При отказе обязательной записи аудита сервер возвращает `503` и откатывает транзакцию.
Подтверждение поступления денег и вызовы webhook не снимают административную блокировку.
